# Phase 2 — LiDAR data inspection: findings and Phase 3 recommendations

*Date: 2026-11-04. Data: the 10 files in `data/raw/pointclouds/` (opened read-only).*

This document interprets the measured results. The full tables come from the real data
and are regenerated by the code:

* `outputs/reports/lidar_inspection_report.md`: human-readable tables
* `outputs/reports/lidar_inspection_report.json`: every measurement, machine-readable
* `outputs/reports/lidar_previews/`: figures and georeferenced GeoTIFF previews

Regenerate (use the **activated** environment, see §8):

```powershell
micromamba run -n roadmarking-ai python scripts/inspect_lidar.py stats --force
micromamba run -n roadmarking-ai python scripts/inspect_lidar.py report
```

**Labels used below:** *measured* = exact statistic over decoded, validated points.
*Estimate* = derived via a model or heuristic (corridor axis, road-candidate mask).
*Hypothesis* = plausible but unverified; needs client confirmation.

## 1. Input data characteristics

### 1.1 File integrity — the most important finding

| File | Size | Header points | Valid points used | Problem |
|---|---:|---:|---:|---|
| Job_20251118_1121_Track01-1 | 383 MB | 42,970,233 | 39,470,233 (91.9 %) | 70 of 860 LAZ chunks corrupt |
| Job_20251118_1121_Track03-2 | **0 bytes** | — | 0 | Empty file |
| Job_20260325_0838_Track01_1 | 210 MB | **0** | 0 | Header never finalised (count 0, invalid bounds, chunk-table pointer unset): an export that did not finish |
| Job_20260325_0838_Track01_2 | 260 MB | 31,824,108 | 19,574,108 (61.5 %) | 245 of 637 chunks corrupt |
| Job_20260325_0838_Track01_3 | 243 MB | 30,509,631 | 30,509,631 | Intact |
| Job_20260325_0838_Track01_4 | 233 MB | 29,685,816 | 26,435,816 (89.1 %) | 65 of 594 chunks corrupt |
| Job_20260325_0838_Track01_5 | 223 MB | 28,930,197 | 28,330,197 (97.9 %) | 12 of 579 chunks corrupt |
| Job_20260325_0838_Track01_6 | 253 MB | 31,266,745 | 28,116,745 (89.9 %) | 63 of 626 chunks corrupt |
| Job_20260325_0838_Track01_7 | 280 MB | 33,772,951 | 32,972,951 (97.6 %) | 16 of 676 chunks corrupt |
| Job_20260325_0838_Track01_8 | 271 MB | 32,870,412 | 32,870,412 | Intact |

**Total:** 261.8 M header points, **238.3 M valid (91 %)**. Only 2 of 10 files are fully intact.

**How the corruption shows up (measured):**
* Corrupt LAZ chunks do **not** always raise an error. They often decode "successfully"
  into garbage: coordinates spread over ±2,000 km, NaN GPS times, return number greater
  than the number of returns.
* Ordinary readers stop at the first bad chunk: laspy stops with "failed to fill whole
  buffer", and **PDAL crashes** (access violation `0xC0000005`).
* The byte layout and chunk table are consistent, and there are no zero-filled blocks.
  So this is not a truncated or interrupted copy. Corrupt chunks hold different
  (non-zero) bytes, about 1.0–1.5 % zero bytes vs about 0.4 % in valid chunks.
  **The cause cannot be determined from the files.**

**What the project now does:** `roadmarking.io.pointcloud.iter_laz_chunks`
* decodes each LAZ chunk independently via the chunk table;
* checks every point (inside header bounds, `1 ≤ return_number ≤ number_of_returns`,
  finite GPS-week time);
* discards any chunk containing an invalid point **entirely**, because plausible-looking
  garbage can come before the first detectable invalid point.

Points are stored in acquisition order, so **each discarded chunk is a missing stretch of
road**: the rectangular gaps in `Job_20260325_0838_Track01_2_overview_1m.png`. In
Track01_2 the southern ~45 % of the corridor is fragmented. PDAL reads the two intact
files correctly (30.5 M points in 5 s, 32.9 M in 6 s).

### 1.2 Header and attributes (measured, all usable files)

* **LAS 1.2, point format 3** (XYZ, intensity, returns, classification, scan angle, user
  data, point source ID, GPS time, RGB). Scale 0.001 m. Offsets differ per file.
  No extra dimensions.
* **No CRS anywhere.** No GeoKey/WKT VLRs. Global encoding = GPS week time. No generating
  software is recorded; creation date 2026-10-20 (the export date, not the flight date).
* **Coordinates:** X ≈ −58 k … −44 k, Y ≈ −118 k … −86 k, Z ≈ 13 … 86 m. Units are not
  declared. The magnitudes look like metres in a projected national grid.
  *Hypothesis:* negative coordinates of this size, together with the Portuguese attribute
  schema, fit PT-TM06/ETRS89 (EPSG:3763). **This is not assumed anywhere in code**; the
  client must confirm the CRS and the vertical datum.
* **Classification: all points are class 0** (never classified).
* **Point source ID = 0 and scan angle = 0 for every point** (fields not populated). Flight
  lines or passes cannot be separated by ID.
* **Returns:** 87–94 % single returns. Up to 4 returns, mostly on vegetation.
* **RGB present:** 8-bit colour stored scaled ×257 (min 257 = 1×257). Probably colourised
  from imagery; alignment with the LiDAR is unverified.
* **GPS time:** the eight March files are consecutive (≈ 108 s each), i.e. one continuous
  trajectory split into `Track01_1 … _8`. The November file is a separate 70.7 s capture.
* **Intensity:** 16-bit, observed min 118 in every file, max 65,535 (see §3).

### 1.3 Acquisition geometry (estimates from the 1 m grid and GPS time)

| | November file | March files |
|---|---|---|
| Corridor length per file | 1.4 km | ≈ 2.2 km |
| Platform speed | 19.9 m/s | 18.5–20.4 m/s (≈ 72 km/h) |
| Point rate | ≈ 608 k pts/s | ≈ 267–312 k pts/s |
| Swath width (median) | 137 m | 125–152 m |
| Density within ±10 m of the corridor axis | ≈ 875 pts/m² | ≈ 286–379 pts/m² |
| Density 40–50 m to the side | ≈ 20 pts/m² | ≈ 13–24 pts/m² |

**Observation about the platform.** Density is concentrated on a ~20 m band and falls by
**10–100×** within 20–90 m to the side, with occlusion shadows (dips and recoveries across
the swath). Nearest-neighbour spacing along scan lines is **≈ 9 mm**. A conventional aerial
survey normally gives a fairly even density across its swath. This profile fits a sensor
**very close to the road surface**: a vehicle-mounted mobile scanner, or a UAV flying very
low along the road. The project brief states aerial/drone LiDAR, and the data alone cannot
settle it. **Please confirm the platform and sensor with the client.** It matters mostly
for intensity normalisation (range and incidence dominate the intensity) and for what a
trajectory file would make possible.

## 2. Point density

Measured on **road-candidate 1 m cells** (§4), never on the bounding box. Bounding-box
"density" (10.7–50.5 pts/m²) understates road density by 20–70×.

| File | Road cells p5 | p25 | **p50** | p95 | Road cells < ½ median |
|---|---:|---:|---:|---:|---:|
| Nov Track01-1 | 84 | 415 | **1,032** | 3,045 | 30 % |
| Mar Track01_2 | 166 | 322 | **723** | 1,739 | 28 % |
| Mar Track01_3 | 180 | 351 | **773** | 1,745 | 27 % |
| Mar Track01_4 | 177 | 334 | **742** | 1,750 | 28 % |
| Mar Track01_5 | 20 | 228 | **563** | 1,729 | 32 % |
| Mar Track01_6 | 168 | 308 | **732** | 1,735 | 30 % |
| Mar Track01_7 | 182 | 342 | **750** | 1,739 | 27 % |
| Mar Track01_8 | 180 | 333 | **767** | 1,744 | 29 % |

**Nearest-neighbour spacing** (exact KD-tree, XY, road points, 64 random 8 m × 8 m
samples, 8 per file): median NN distance per sample **0.008–0.052 m (median 0.009 m)**, at
sample densities of 94–1,602 pts/m² (median 776). A uniform pattern at 776 pts/m² would
give ≈ 3.6 cm. **Sampling is strongly anisotropic:** points sit very close together along
scan lines, with wider gaps between lines (visible as striping in every preview).

**Local variation.** About 27–32 % of road cells have less than half their file's median
density. This is mainly the across-track gradient: far lanes and hard shoulders are
sparser. The near carriageway in one November window measured 2,236 pts/m² against
96 pts/m² on the far carriageway in the same window.

**Missing data.**
* On the road surface itself there are 0–13 empty 1 m cells per file inside the road
  corridor, so coverage at 1 m is essentially complete wherever data exists.
* The real gaps are (a) **the discarded corrupt chunks** (whole stretches) and
  (b) **the two unusable files**.
* At sub-decimetre pixel sizes there are systematic between-scan-line gaps (§5).

**Can 15 cm markings be resolved?** Yes, on most of the road.
* At the median road density (~750 pts/m²) a 15 cm wide line receives about 110 points
  per metre of length.
* At the 5th percentile (≈ 170 pts/m² in March) it still receives about 25 points per
  metre.
* The exception is the sparsest edge of some files (Track01_5 p5 = 20 pts/m², ≈ 3 points
  per metre). There, thin markings are only marginally resolvable.

## 3. Intensity

**Measured, all valid points:**
* Every file uses the full 16-bit range. The minimum is a constant 118. There are **no
  zero-intensity points**.
* Medians are 5.5–7.6 k; p99 is 36–62 k.
* Points at 65,535 (saturated): **0.78 %** in the November file, **0.013–0.11 %** in the
  March files.
* Histograms (`intensity_histograms.png`) have two modes: asphalt around 5 k, and a broad
  mode at **30–45 k** in the March data, most likely paint. The November file has extra
  mass at 50–65 k plus the saturation spike: its brightest paint is clipped.

**Variation by region** (median road intensity per 100 m block, `regional_road_intensity.png`):

| | Block medians | Max/min within file |
|---|---|---:|
| November file | 5.1–9.0 k (median 7.7 k) | 1.77 |
| March files 2–4 | ≈ 4.4–6.9 k | 1.13–1.52 |
| March files 5–8 | ≈ 4.9–7.2 k | 1.13–1.46 |

* Within the **single continuous March flight**, road intensity shifts by **≈ +20 %**
  between files 2–4 and 5–8.
* The two acquisitions differ by about 1.3–1.6× (November road median ≈ 7.7 k vs March
  ≈ 4.8–6.0 k).
* Paint contrast also differs visibly: March dashes and arrows are much fainter relative
  to the asphalt than the November edge lines and chevrons.

**Normalisation candidates** (figures `*_normalization.png`, computed on observed pixels
only):

* *Raw min–max:* dominated by the near-lane gradient and by saturated points.
* *Global p1–p99 of road pixels:* removes file-level offsets. But within a single window
  the asphalt background visibly differs between near and far lanes (not yet quantified),
  so one scaling does not fit the whole road.
* *Local background division* (pixel / median of all observed pixels in its 2.5 m block):
  equalises near and far lanes and reveals faint markings in sparse areas. Example: dashes
  at x ≈ −44,400, y ≈ −117,858 in the November window are visible only in this version.
  But it also amplifies noise where density is low. A 2.5 m block median is not moved by
  a 15 cm line, but wide painted areas (chevron fields, bands) can raise the local median.

**Conclusion:** markings **cannot** be found with one global fixed threshold. Background
level varies by acquisition (×1.3–1.6), by segment within a flight (≈ ×1.2), and visibly
across the road between near and far lanes. Paint contrast also varies. Low-intensity
points were not filtered out anywhere.

## 4. Road-surface assessment

* **Existing classification is useless** (all class 0).
* **Geometric criteria work.** On a 1 m grid:
  - ≥ 4 points per cell;
  - ≥ 95 % single returns (vegetation is multi-return);
  - z-range ≤ 15 cm within the cell (excludes vehicles, kerbs, walls, barriers);
  - slope ≤ 12 % between neighbouring cells;
  - part of a connected smooth area ≥ 200 m² (roofs are isolated by their walls).

  This finds the carriageways. In the two carriageway regions checked cell by cell against
  a preview, 99.6 % and 98.1 % of the visibly paved cells are accepted (a spot check, not
  a validation).
* **A height-above-local-minimum test was tried and rejected.** It discarded 80 % of a
  carriageway on an **embankment**, where the nearby ditch is more than 0.5 m lower. The
  corridor has embankments, so Phase 3 must not use "lowest local point = road".
* **Still confused** (it's an estimate): hard shoulders, paved verges and lay-bys pass as
  "road"; large flat roofs (> 200 m²) would pass. None were seen in this corridor, which is
  mostly vegetation either side. Vehicles show up as non-flat cells plus occlusion shadows.
  Bridges were not assessed.
* **Candidate road area:** 16.6 ha over ≈ 16.3 km of corridor, about 10 m average
  width, which is narrower than the full paved width because sparse far-lane cells are
  sometimes excluded.

**Recommended Phase 3 strategy:**
1. Ground filtering with PDAL `filters.smrf` (or `filters.csf`). This works on intact
   files; corrupt files must first be read with `iter_laz_chunks` and written to a clean
   interim copy, never overwriting the originals.
2. Road = ground ∩ smooth ∩ single-return ∩ large connected component, using the
   criteria above.
3. Refinement: kerb/barrier detection from height steps, plus intensity and RGB (asphalt
   is grey) as supporting evidence. If the client supplies a trajectory, the road band
   around it can serve as a prior.
4. Keep a 5 m buffer around the road so that edge lines and kerb-side markings are never
   clipped.

## 5. Representative previews (observed vs displayed)

There are 16 preview windows (2 per usable file: the highest density of bright,
paint-like road cells, and a median-scoring "typical" window chosen to avoid
cherry-picking), each at 2.5, 5 and 10 cm.

* Every PNG shows **observed-only** intensity (magenta = no point in the pixel). A separate
  panel shows a display-only fill of at most 1 px, tinted cyan so filled pixels are always
  identifiable.
* Every preview also has `*_imax.tif` / `*_count.tif` GeoTIFFs carrying the exact affine
  transform. They have **no CRS**, because none is declared in the source.

**Road no-data share** (pixels on road with zero points), median over all 16 windows:

| GSD | Mean pts/pixel | Observed no-data | Expected for random sampling | 15 cm line width |
|---:|---:|---:|---:|---:|
| 2.5 cm | 0.52 | **69.8 %** (50–80 %) | 59 % | 6 px |
| 5 cm | 2.1 | **26.4 %** (7–49 %) | 12 % | 3 px |
| 10 cm | 8.4 | **0.2 %** (0–26 %) | ≈ 0 % | 1.5 px |

Observed no-data is about 2× the random-sampling expectation because of the scan-line
pattern. The gaps at 5 cm are mostly 1 px slivers between scan lines.

**What is visible (visual inspection of the previews):** solid edge lines, broken lane
lines, chevron/diagonal hatching in gore areas, and a directional arrow (faint, March data)
are clearly recognisable at 5 cm. At 2.5 cm they are recognisable only with gap filling. At
10 cm the lines are 1–2 px wide, so width and dash-end positions are coarse. No annotations
or reference GIS were supplied yet (`data/raw/annotations/` and `reference_gis/` are
empty), so visibility has **not** been checked against ground truth.

## 6. Recommended rasterization configuration (for Phase 3)

| Setting | Recommendation | Reason (measured evidence) |
|---|---|---|
| Ground pixel size | **5 cm** fixed | Mean 2.1 pts/px on road; 15 cm line = 3 px; no-data 26 % (mostly 1 px scan-line slivers). 2.5 cm leaves ~70 % of road pixels empty; 10 cm makes 15 cm lines 1.5 px, too coarse for LARGURA/TRAÇO/ESPAÇO. |
| Adaptive resolution | **Do not vary pixel size**; handle density through channels | One pixel size keeps the model's scale constant and tile georeferencing simple. Density varies ~10× across the road, which a count/validity channel conveys better than resampling. |
| Rasterization method | Point binning (no interpolation) on a north-up grid | Every value stays traceable to measured points; no TIN surface invents paint. |
| Intensity aggregation | Keep **max** and **mean** per pixel (and count) | Max emphasises thin bright paint at 2 pts/px; mean is robust to single spikes and saturation (0.01–0.8 % at 65,535). Saturated points are flagged, not removed. |
| Model input (3-channel slot) | Candidate: [locally normalised max, segment-normalised mean, observation/log-count channel] | Uses Mask2Former's 3-channel input without stacking identical copies. **To be validated** in Phase 3/5 against annotations. |
| No-data handling | `count == 0` → no-data; fill **only isolated ≤ 1 px gaps** for model input, recorded in the observation channel; never fill larger gaps | 5 cm gaps are mostly 1 px slivers; larger gaps are real lack of data and must not become "paint". |
| Intensity normalisation | Robust percentiles of road pixels per ~100 m segment (file-level and segment-level offsets), plus local background division (2.5 m block median) as a second channel. No global threshold. | ×1.3–1.6 between acquisitions, ≈ ×1.2 between segments, visible near/far-lane differences. Local division reveals faint markings in sparse areas. |
| Tile size | **1024 × 1024 px = 51.2 m** | Covers a full carriageway width plus margins in one tile. |
| Tile overlap | **256 px = 12.8 m** (instead of 128) | Arrows, inscriptions and chevron groups must appear whole in at least one tile so cross-tile merging is rarer. Cost: 776 instead of 650 tiles. |
| Tiles to process | Only tiles touching the road corridor (road + 5 m) | 776 tiles for the whole dataset, vs ≈ 6.65 Gpx if each file's bounding box were rasterised. |
| Pixel ↔ world | North-up affine; origin snapped to integer multiples of the pixel size in source coordinates; pixel-centre convention; transform stored with every tile (GeoTIFF) | Tiles from different files align exactly; uses the existing `north_up_transform` / `pixel_to_world` (unit-tested). |
| CRS | Keep source coordinates untouched; write **no CRS** until the client confirms one | No CRS in the data; guessing would corrupt every GIS deliverable. |
| Z for later stages | Store per-pixel `z_min` only as a reference; Stage 8 takes Z from the original points | Keeps original 3D coordinates authoritative. |

## 7. Performance considerations (measured where stated, otherwise estimates)

* **Data volume:** 2.30 GiB LAZ, 261.8 M points, ≈ 16.3 km of corridor, i.e. ≈ 145 MB and
  ≈ 16 M points per km.
* **Decoding (measured, i7-12700F):**
  - chunk-table reader with statistics: 30–52 s per ~30 M-point file, one thread;
  - PDAL on intact files: 5–6 s per file.

  Files are independent, so they can be processed in parallel (20 hardware threads).
* **RAM (measured):** the streaming report process peaked at ≈ 1.1 GB working set. Loading
  a whole file into memory would take roughly 2–3 GB per file (34 B packed record plus
  24 B float64 XYZ per point); feasible with 64 GB but unnecessary. **Design rule:**
  stream 50 k-point LAZ chunks, accumulate per tile, write tiles incrementally.
* **Raster memory (estimates, 18 B/px = 4 float32 channels + uint16 count):**

  | | Road corridor (31.4 ha) | Bounding box |
  |---|---:|---:|
  | 5 cm | 125 Mpx ≈ 2.3 GB for the whole dataset | 6.65 Gpx ≈ 120 GB |
  | 2.5 cm | 502 Mpx ≈ 9 GB | — |

  **Never rasterise bounding boxes.**
* **Tiles:** 776 at 5 cm with 256 px overlap (650 with 128 px; 1,597 at 2.5 cm).
* **Disk (estimate):** 776 tiles × 3 channels × 1024² stored as uint16 ≈ 6 MB per tile
  uncompressed, i.e. ≈ 5 GB; deflate typically less. Plenty of free space (D: 334 GB).
* **GPU:** RTX 3050, 6 GB. Mask2Former Swin-S on 1024² tiles has **not** been run yet
  (pretrained weights are not downloaded). Expect batch size 1–2 with fp16/bf16 and
  possibly gradient checkpointing for training. **No speed figures are claimed**; they
  will be measured in Phase 5.

## 8. Known limitations and open issues

1. **Data integrity:** 2 files unusable, 6 of the remaining 8 partly corrupt (9 % of points
   discarded overall, 38.5 % in Track01_2). **Re-delivery with checksums is needed.**
2. **CRS and vertical datum unknown.** Coordinates are kept as-is.
3. **Platform unconfirmed** (§1.3), and there's no trajectory file, so range/incidence
   intensity correction isn't possible yet.
4. The road-candidate mask is a heuristic estimate (may include shoulders and verges, can
   miss sparse far-lane cells). Density and intensity "on road" inherit that uncertainty.
5. Previews are 2 windows per file and NN samples 8 per file. They are representative but
   not exhaustive.
6. No annotations or reference GIS have been supplied, so marking visibility is judged
   visually only.
7. The November and March acquisitions differ (point rate ×2, road intensity level
   ×1.3–1.6, saturated-point share ×7–60). They should be treated as separate domains when training.
8. **Environment issues found in this phase:**
   * The env's `python.exe` must be run through the **activated** environment
     (`micromamba activate` / `micromamba run`). Otherwise numpy/scipy linear algebra
     crashes (`0xC06D007F`): conda-forge's BLAS loads a further DLL lazily, and Windows
     only finds it via `PATH`. A health check and a test now detect this.
   * **PyTorch and conda's MKL brought two OpenMP runtimes** (fixed 2026-11-04). Any
     process using torch and numpy/scipy linear algebra failed in either order
     (`OMP: Error #15` / `WinError 127` on `shm.dll`). Fix applied with approval: conda BLAS
     switched from MKL to OpenBLAS (`libblas`, `libcblas`, `liblapack` → `*openblas`,
     plus `libopenblas` 0.3.34 pthreads; no other packages changed), pinned in
     `environment.yml` and the lock file. Verified: both import orders work, including
     CUDA; the full suite passes in one process (57 passed, 1 skipped); health check
     10/10.

## 9. Final recommendations for Phase 3

1. **Get the data fixed first:** re-exports of `Track01_1` and `Track03-2`, a re-delivery
   (with checksums) of the six partly corrupt files, the CRS and vertical datum, the
   platform/sensor, and the trajectory if available.
2. ~~Approve the BLAS/OpenMP environment fix~~: done (§8).
3. Preprocessing: stream with `iter_laz_chunks` → write clean interim LAZ/COPC per file
   (originals never touched) → ground/road extraction as in §4.
4. Rasterise the road corridor only, at **5 cm**, with max/mean/count channels, the
   no-data rules of §6, and global-grid-aligned **1024 px tiles with 256 px overlap**.
5. Implement and compare the two normalisations (segment percentiles vs local background
   division) on the intact files, then pick one once annotations exist.
6. Treat the November and March acquisitions as separate domains in dataset splits.
